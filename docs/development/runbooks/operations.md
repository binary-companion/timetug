# TimeTug operations reference

Historical detailed recipes moved from the root guide on 2026-09-26. Check current architecture and workflow files before acting.

TimeTug is a macOS menu bar app that takes over the screen before meetings. Start with
`docs/architecture.md`; the 2026-09-18 core design is historical where later decisions differ.

## Layout
- `Packages/TimeTugCore`: pure Swift, platform-neutral logic. NO UI or Apple-only imports.
- `Packages/EventKitSource`: Apple Calendar adapter (macOS only); speaks the library's `CalendarSource`.
- `Packages/CalendarConnectors`: portable connector library (ADR 0012), no external dependencies, pure Swift that builds on Linux. Products: `CalendarCore` (model, `CalendarSource`, `ConnectorKind`, `ChangeMonitor`, `AllDay`, `ConferenceDetector`, connection/sync stores and optional write API), `CalendarOAuth` (OAuth PKCE and refresh), `GoogleCalendar`, `MicrosoftCalendar`, `ICalendar`, `CalDAVCalendar`, `ICalSubscription` and `CalendarTestSupport`. Imports nothing from TimeTug. The host app supplies credential storage, OAuth interaction and persistence; Microsoft sign-in remains read-only (ADR 0017) while library write code remains available.
- `Packages/CalendarBridge`: minimal glue. `EventMapper` wraps library events in `TimeTugCalendarEvent` (drops cancelled ones, adds calendar info); `ConnectedSource` adapts a library source to Core's source protocol and translates errors and changes.
- `Packages/CalendarApple`: Apple-side adapters for the library (Keychain `CredentialStore`, loopback OAuth interaction, `WebAuthenticationSessionPresenter` (the `ASWebAuthenticationSession` sign-in sheet), `CryptoKitSHA256`, injected in `AppConnectors.swift`).
- `Packages/AppleIntelligenceInference`: Apple on-device model adapter for duplicate detection (macOS 26+, compile-guarded). Only place with Foundation Models imports.
- `Apps/macOS`: AppKit/SwiftUI shell. Generated Xcode project (XcodeGen).
- `Apps/macOS/Sources/UpdateController.swift`, `UpdatesSection.swift`: Sparkle in the app layer only (never Core). Beta opt-in is `updates.includeBetas.v1` in UserDefaults.
- `Apps/macOS/Widgets`: WidgetKit extension `TimeTugWidgets` (Next Up, Today, and macOS 26 Control Center controls). Reads the snapshot; no EventKit.
- `Apps/macOS/Shared`: AppGroup, SharedSettings, SettingsChangeSignal, WidgetSnapshotStore. Compiled into both the app and the extension.
- `artwork/`: brand images (see `docs/ARTWORK_USAGE.md`); the app's asset catalog is `Apps/macOS/Resources/Assets.xcassets`. Do not use the app icon for the menu bar; the menu bar icon is the puppy set (`MenuBarPuppyLight`/`MenuBarPuppyDark` idle, chosen by the menu bar's appearance, and `MenuBarPuppyColor` while a meeting is near), picked by `MenuBarIconState.assetName(darkMenuBar:)`.

## Rules
- Core answers "what and when". The app answers "how it looks and where it lives". If code needs a window, tray or pixel, it belongs in the app.
- Dependencies point toward Core and the connector library. The current module graph is in `docs/architecture.md` and enforced by `scripts/ci/check-architecture.sh`; keep both current when adding a package. The app owns source configuration UI and credential storage. Source packages contain no UI.
- Time is always passed in (`now: Date`); never call `Date()` inside Core logic.
- Core has no display strings. Formatting belongs to the front end.
- Every Core behavior has a Swift Testing test. Write the failing test first.
- Record significant decisions in `docs/decisions/` (ADR, one file each).

## Commands
- Core tests: `swift test --package-path Packages/TimeTugCore`
- EventKitSource tests: `swift test --package-path Packages/EventKitSource`
- Bridge tests: `swift test --package-path Packages/CalendarBridge`
- Apple adapter tests: `swift test --package-path Packages/CalendarApple`
- Connector library tests: `swift test --package-path Packages/CalendarConnectors`.
- Inference package tests: `swift test --package-path Packages/AppleIntelligenceInference`
- Generate app project: `xcodegen generate --spec Apps/macOS/project.yml`
- Build app: `xcodebuild -project Apps/macOS/TimeTug.xcodeproj -scheme TimeTug -destination 'platform=macOS' build`
- App tests: `xcodebuild -project Apps/macOS/TimeTug.xcodeproj -scheme TimeTug -destination 'platform=macOS' test`
- Window/status-item behavior is verified by hand: `docs/manual-tests/macos-checklist.md`.

## Gotchas
- App and EventKitSource use Swift 5 language mode; Core uses Swift 6.
- Generated `*.xcodeproj` is git-ignored; regenerate after editing `project.yml`.
- The app depends on the remote package KeyboardShortcuts, pinned exactly in `Apps/macOS/project.yml`; regenerate the project after changing it (first build needs network). Keep it at 3.1.0 or newer: 2.x silently drops modifier key combos in the Settings recorder on macOS 27.
- Calendar access needs the calendars entitlement and `NSCalendarsFullAccessUsageDescription`. EventKit attendee lookup (participants with no `mailto:` address) also needs the `com.apple.security.personal-information.addressbook` entitlement and `NSContactsUsageDescription`; the prompt appears once, never blocks a read, and denying it just leaves those emails nil.
- Takeover decisions are logged (titles redacted). Read them with ``log show --predicate 'subsystem == "com.timetug.app" AND category == "takeover"' --last 1h``. The active ledger is `AppSupportFiles.url("takeover-ledger.json")`: in the App Group's `TimeTug/` folder for team-signed builds, or the legacy Application Support folder for ad-hoc builds. Inspect the active location before resetting it; see the `diagnosing-takeovers` task skill.
- Duplicate detection: rules run always; on-device inference is opt-in (Settings > Calendars, Beta), default off. Lessons and verdicts live at `AppSupportFiles.url("dedup-state.json")` under the same App Group or ad-hoc fallback. Do not reset the old Application Support copy while a team-signed build is using the group copy.
- Widgets and controls only work in team-signed builds. Local signing: put `DEVELOPMENT_TEAM`, `CODE_SIGN_STYLE` and `CODE_SIGN_IDENTITY` in `~/.config/timetug/signing.xcconfig` (outside the repo; the team id is public, certificates stay in the keychain). `scripts/dev/link-signing.sh` (run by xcodegen's `preGenCommand`) links it into each checkout as the git-ignored `Apps/macOS/Config/Local.xcconfig`, which `Config/Signing.xcconfig` includes; with no such file builds are ad-hoc signed (CI). Xcode cannot include a file by `$(HOME)`, hence the link. Automatic `Apple Development` signing needs Xcode signed in to the Apple ID (Xcode > Settings > Accounts); manual Developer ID also works (no debugger). After changing signing, do a `clean` build (a stale ad-hoc extension fails with "Embedded binary is not signed with the same certificate"). To reproduce CI locally: `TIMETUG_SIGNING_XCCONFIG=/nonexistent xcodegen generate --spec Apps/macOS/project.yml`. `DEVELOPMENT_TEAM` is deliberately not in `project.yml`. Checks in `docs/manual-tests/macos-checklist.md`. Ad-hoc builds run normally: the snapshot write logs and skips, and widgets show the placeholder. See ADR 0010.
- `WidgetSnapshotStore` writes `agenda-snapshot.json` directly in `AppGroup.containerURL`, while `AppSupportFiles.url(_:)` keeps app-state files in its `TimeTug/` subfolder. Do not construct a `~/Library/Group Containers/…` path: use those APIs because the real location depends on signing and sandbox access. Some shells cannot read the group container (privacy protection). Control Center intents live in the extension, write the shared suite and signal the app with a Darwin notification; the app re-reads.
- Google accounts need an OAuth client: a git-ignored `Apps/macOS/Config/GoogleOAuth.xcconfig` (or `~/.config/timetug/google-oauth.xcconfig`, linked in by `scripts/dev/link-signing.sh`) defining `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`. Without it Google is simply not offered in Settings > Accounts. Beta and release builds get the client from the optional repository secrets `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`: only the `Build Release app` steps of `beta.yml` and `release.yml` receive them (never `ci.yml`), `scripts/ci/google-oauth-config.sh` writes a mode-600 temp xcconfig and exports `TIMETUG_GOOGLE_XCCONFIG` before `xcodegen generate`, and `build-release.sh` checks the built Info.plist and prints only "configured" or "absent". The secret is a Desktop-app client secret that Google treats as non-confidential (it ships inside the app), but it must stay out of git.
- Microsoft accounts need an Entra app registration's client id (a public client, no secret): a git-ignored `Apps/macOS/Config/MicrosoftOAuth.xcconfig` (or `~/.config/timetug/microsoft-oauth.xcconfig`, linked in by `scripts/dev/link-signing.sh`) defining `MICROSOFT_OAUTH_CLIENT_ID`. Without it Microsoft shows as unavailable in Settings > Accounts. Beta and release builds get it from the optional repository secret `MICROSOFT_OAUTH_CLIENT_ID` through `scripts/ci/microsoft-oauth-config.sh`, the same way as Google (never `ci.yml`).
- Google sign-in opens in a system web-authentication sheet (`ASWebAuthenticationSession`), which shares Safari sessions, passkeys and autofill. It closes itself because the loopback listener answers the redirect with a 302 to `timetug-oauth://done`, which the sheet catches. The hidden switch `defaults write com.timetug.app oauth.useBrowser.v1 -bool true` (`BrowserPreferringPresenter`, read on every sign-in; `defaults delete com.timetug.app oauth.useBrowser.v1` to undo) sends sign-in to the default browser instead, because Google's verification demo video must show the OAuth client ID in the browser address bar, which the sheet does not show. An embedded web view is not an option: Google blocks embedded user agents. If the sheet cannot start, the flow falls back to the default browser and the plain "You're signed in" page; cancelling the sheet ends the flow at once.
- `xcodegen generate` rewrites checked-in Info.plists for the direct app, widgets and App Store targets. `project.yml` owns their properties; inspect generated diffs and keep intentional privacy, OAuth and entitlement changes rather than blindly restoring them.
- `keychain-access-groups` is restricted: the App Store target carries it, and the direct distribution gains it only when `sign-app.sh` embeds a Developer ID provisioning profile. Ad-hoc and ordinary Xcode builds cannot launch with that entitlement. `AppCredentials` uses the shared group only when the running build holds it (ADR 0019).
- Calendar writes are opt-in: `capabilities.canWrite == (source is WritableCalendarSource)`, unsupported fields throw `WriteError.unsupported`, updates send only changed fields and a stale version is judged per field against `EventPatch.base`. Live write tests never run in CI; use the `running-live-calendar-tests` skill and a dedicated account. Microsoft sign-in currently grants read-only scopes (ADR 0017), so its library write smoke test requires separate write-capable consent and is not evidence for the shipped app connection.
- `TimeTugCore` and `CalendarCore` both define `CalendarSource` and `SourceError`: inside Core the local declaration shadows the import; elsewhere qualify (`CalendarCore.SourceError`). All-day events belong to a day by calendar date in the event's own zone (`TimeTugCalendarEvent.allDayDates/covers`), never the viewer's zone; `CalendarStore` queries sources with a 26 hour margin each side (`sourceQueryMargin`).
- A calendar that is not shown never tugs: `TakeoverPolicy` requires an opted-in copy on a calendar that is not hidden, and saved settings that both hide and opt in a calendar decode as hidden. The Calendars pane sets system-style calendars (`CalendarKind`: birthdays, subscribed feeds, from EventKit and Google ids) apart unless Tug is on for them.
- Enable Tug is enforced in Core (`TakeoverPolicy.qualifies` via `TakeoverSettings.enabled`, default on), not in the app. Declined events never take over (no setting); "Require a video link" and "Require other attendees" are off by default. `TakeoverSettings` still decodes the retired `disabled` and `skipSoloEvents` keys so saved choices carry over; the shared-suite key is `shared.enableTug` (the old `shared.disableTug` is unused).

## CI and releases
- `.github/workflows/ci.yml`: on push to `master` and every PR (build and tests only; PRs get no signing, deployment or OAuth secrets, and nothing that can enter the update feed). The required `core-linux` job may use a read-only Docker Hub pull token on internal PRs; forks receive none. Jobs: `release-tooling` (release scripts, workflow contracts and website tests), `core` (tests for Core, the connector library, CalendarBridge, CalendarApple, EventKitSource and the inference package), `app` (XcodeGen + app tests, uploads the `.xcresult` on failure), `dmg` (unsigned DMG), `core-linux` (required; swift:6.0; runs the Core and connector library tests to prove both stay portable).
- `.github/workflows/release.yml`: two starts, both with a `v*` tag on `master` and owner-written notes: save a DRAFT release and run the workflow manually (`workflow_dispatch` with `tag`; a saved draft fires no event), or PUBLISH the release in the UI (`release: published`; the assets are then attached to it, visible without assets for ~30 min). No tag-push trigger (publishing creates the tag and would fire both). GitHub immutable releases are currently OFF; if turned on, only the draft flow works and `scripts/release/release-state.sh` (`none|draft|published|published-immutable`) makes the run fail early on an immutable published release. Builds the tag's commit (must be on `master`; needs approval via the `release` environment) with `scripts/ci/build-release.sh`; signed and notarized DMG when the Apple secrets exist, otherwise an unsigned prerelease DMG (`scripts/release/`). `scripts/release/upload-release-assets.sh` attaches the DMG, `.sha256` and Sparkle zip (draft: upload then publish, creating the tag if missing; published: `gh release upload --clobber`; none: create), then the appcast item is added (a `-` tag or a release marked prerelease goes to the beta channel; unsigned never does). A release event checks out `refs/tags/<tag>` (a same-named branch cannot shadow it) and a `Validate the tag` step rejects a bad tag (e.g. `V1.2.3`) before any build. Fails early if the Apple secrets exist without `SPARKLE_PRIVATE_KEY`. Tag `v1.2.0` is burned (published and locked while immutability was on); use `v1.2.1` or higher. Release naming, notes and version-bump rules (default bump minor, major and trivial on request, explicit version overrides) are in `docs/release.md` "Release rules"; follow them when preparing a release. Process and secret setup are in `docs/release.md`; rationale: ADR 0007, 0008, 0011.
- `.github/workflows/beta.yml` (`Beta`): `workflow_run` of `CI` on `master` pushes that passed, same repo. Builds only the tip of `master` (skips with a notice if a newer commit exists) and skips if the signing secrets are missing. Versions from `scripts/ci/compute-versions.sh beta`, signs with Developer ID (no notarization), publishes a `beta-<build>` prerelease, then updates the appcast on `gh-pages` (keeps 5). No approval; secrets are only used on merged code, so keep `master` protected. Rationale and risk: ADR 0011.
- Sparkle scripts in `scripts/release/`: `sign-app.sh`, `make-update-zip.sh`, `fetch-sparkle-tools.sh` (pinned in `sparkle-version.txt`), `publish-appcast.sh`, `appcast.py`. Gotcha: `CFBundleVersion` is a UTC timestamp `YYYYMMDDHHMMSS` (14 digits) from `compute-versions.sh`; never a hash or `GITHUB_RUN_NUMBER`. Beta display versions are `<newest stable v* tag>-beta.<BUILD_NUMBER>`; no manual bump (the `project.yml` value is only the fallback when no stable tag exists).
- Gotcha: `SUFeedURL` and `SUPublicEDKey` live in `project.yml` `info.properties`; Sparkle is `exactVersion`-pinned there and in `sparkle-version.txt` (keep both equal). The private key is only the `SPARKLE_PRIVATE_KEY` secret.
- The `dmg` CI job builds and verifies an unsigned DMG on every run and uploads it as the `TimeTug-dmg` artifact.
- DMG scripts: `scripts/release/make-dmg.sh` (dmgbuild, pinned in `scripts/release/dmg/requirements.txt`, installed in `build/dmg-venv`), `scripts/release/verify-dmg.sh <dmg>`, `scripts/release/sign-and-notarize.sh [app|dmg]`. Gotcha: the DMG background PNGs are committed; after editing `scripts/release/dmg/generate-background.swift` re-run it and commit the PNGs, and keep the icon positions in `scripts/release/dmg/settings.py` in sync with the arrow.
- When CI fails: reproduce with the Commands above; for the app job download the `TestResults` artifact. Runner label or Xcode problems: `scripts/ci/select-xcode.sh` and the `runs-on` lines. Keep logic in the scripts, not in YAML.
- Never commit certificates or keys (`*.p12`, `*.p8`, ...); they are git-ignored.
