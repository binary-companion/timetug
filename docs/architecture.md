# Architecture

This is the current module map. The [2026-09-18 core design](superpowers/specs/2026-09-18-timetug-core-design.md) records original rationale; later ADRs and code supersede changed details.

## Modules
- The [timetug-shared](https://github.com/binary-companion/timetug-shared) repository (ADR 0020, ADR 0022), consumed by released version, holds the Rust engine and its tests, the dedup benchmark and the generated Swift package `TimeTugKit`. Windows, Linux and the other platforms are CI targets there.
- **The libraries are Rust (2.0.0, 2026-11-14), and the Mac app runs on them since phase 6 of the [Rust engine program](superpowers/specs/2026-11-10-rust-engine-program-design.md) ([ADR 0023](decisions/0023-mac-app-on-rust-engine.md)).** The app and its three local packages import one module, `TimeTugKit` (product of `timetug-shared` 2.x; the binary target is the prebuilt `TimeTugEngineFFI.xcframework`, a static library, plus the generated Swift and a thin hand-written layer; see `docs/bindings.md` in `timetug-shared`). The connector library [calendar-connectors](https://github.com/binary-companion/calendar-connectors) (ADR 0012) is inside it: the app no longer depends on it directly.
- What the engine owns: the core (`TimeTugCore`'s successor: calendar model, merge and dedup, takeover policy and ledger, the scheduler, the day agenda, widget snapshots), the connectors (Google, Microsoft, CalDAV including iCloud, iCal subscriptions and the system calendar through a host adapter) and the engine proper: one `Engine` that owns the accounts and their lifecycle, refreshes, the fire guard, launch acknowledgement, dedup actions and their persistence, the behaviour settings (through the host's settings storage) and the prompt building and answer parsing for text generation. Front ends send `EngineCommand`s and observe `EngineState` (revisioned) and `EngineEvent`s (`takeoverDue`, `widgetSnapshot`, `joinRequested`, diagnostics). The engine has no display strings and no platform imports. The engine's own files (`connections.json`, `sync-state.json`, the ledger, the dedup state) are read as the Swift engine wrote them.
- The host interfaces the engine calls back into are generated (UniFFI): HTTP transport, credential storage, the system calendar, OAuth interaction, settings storage, diagnostics, the clock, text generation. The Mac implements them in `Apps/macOS/Sources/EngineAdapters` (settings storage over today's UserDefaults keys, OSLog diagnostics, the command queue and state mirror, system event relay) and in the packages below. The engine writes only inside the data directory the host passes (the App Group container); the engine library is statically linked and needs no Rust toolchain to build the app.
- `Packages/EventKitSource`: Apple Calendar adapter (implements the engine's system-calendar interface). Only place EventKit is imported.
- The connector library [calendar-connectors](https://github.com/binary-companion/calendar-connectors) (ADR 0012; Rust from 2.0.0) supplies the connectors inside the engine: Google, Microsoft, CalDAV (including iCloud) and iCal subscriptions, with OAuth (PKCE and refresh), the connection and sync-state stores and an optional write API. The app supplies OAuth client configuration and credentials (see [operations](development/runbooks/operations.md)). Microsoft sign-in requests read-only scopes under [ADR 0017](decisions/0017-microsoft-read-only-scopes.md); the library's write implementation remains available for a host that grants wider scopes. The 1.x Swift branches no longer serve the Mac once the cutover release ships.
- `Packages/CalendarApple`: Keychain credential store (with the migration of items written by the Swift engine), loopback OAuth interaction, the URLSession HTTP transport, all implementing generated host interfaces.
- `Packages/AppleIntelligenceInference`: Apple's on-device model as the engine's text generator (macOS 26+, compile-guarded); the prompt and answer parsing live in the engine. Only place with Foundation Models imports.
- `Apps/macOS`: menu bar item, popover, overlay windows, settings, and the engine host (`AppCoordinator` builds one `Engine` from `AppConnectors.makeConfig` and the adapters in `Sources/EngineAdapters`). `SettingsStore` keeps the presentation settings and mirrors the engine's behaviour settings; `AccountsController` mirrors the engine's account status. XcodeGen builds direct and App Store distributions from one specification; they share an App Group but use separate build directories. The App Store target excludes Sparkle.
- `Apps/macOS/Widgets`: WidgetKit extension (Next Up, Today, macOS 26 controls) that reads the app-written snapshot from the App Group; `Apps/macOS/Shared` holds the code compiled into both targets (ADR 0010).
  The optional global popup shortcut uses the KeyboardShortcuts package (ADR 0005), app layer only.

## Dependencies

The app and the three local packages (`EventKitSource`, `CalendarApple`, `AppleIntelligenceInference`) depend on `timetug-shared` (product `TimeTugKit`) and on nothing else of the libraries; the app also depends on the three packages, KeyboardShortcuts and (direct target only) Sparkle. Inside `timetug-shared` the crates form the layers described in its `docs/architecture.md`. The widget extension does not link the engine: it reads the snapshot the app writes. The app bundle carries the licence notices of the linked engine and KeyboardShortcuts in `Contents/Resources/Licenses/` (build phase `scripts/ci/copy-licence-notices.sh`; reachable from About > Third-party notices). Keep this map aligned with the package manifests and `scripts/ci/check-architecture.sh`; the rules for Core and Bridge are enforced by the same script in `timetug-shared`.

## Flow
EventKit (through the host adapter), Google, Microsoft, CalDAV and iCal subscriptions -> (engine) connector -> store refresh (fetch window) -> snapshot -> scheduler -> one sleep on the engine clock
-> `EngineEvent.takeoverDue` -> (app) `OverlayController` -> join, snooze, dismiss or closed back to the engine (exactly one closing command per `takeoverDue`). `EngineState.agenda` feeds the popover and the status title.
Engine -> `EngineEvent.widgetSnapshot` -> (app) group container (`agenda-snapshot.json`) -> widget timelines. Control Center intents write shared settings and post a Darwin notification; the app sends `settingsChangedExternally` and the engine re-reads them. The app reports wake, clock, day and network changes as `SystemEvent`s and sends `setTimeZone` when the zone changes.

## Adding a calendar source
Implement the connector in the Rust engine (`calendar-connectors` crates, or `timetug-shared` for the engine side): a library pull request and release, then the automatic "Bump timetug-shared to X.Y.Z" pull request here (see AGENTS.md, Repositories, and the `working-across-timetug-repos` skill). No Rust is written in this repository. Apple Calendar is the exception: it stays a host adapter in `EventKitSource`. The app supplies credentials, OAuth interaction and the source's configuration UI, and turns an optional kind on through `AppConnectors.makeConfig`. Never import UI frameworks into the engine or leak provider types into the app's models. A new local package also needs its allowed dependencies and import rules in `scripts/ci/check-architecture.sh`, which fails until it has them.

## Adding a platform front end
Drive an engine: on Swift hosts (macOS, iOS) the `Engine` of the Swift package `TimeTugKit` (generated from the Rust engine, `timetug-shared` `docs/bindings.md`), on Kotlin and Android hosts the generated Kotlin bindings (`kotlin/generated`), on C-capable hosts (Windows, anything else) the C interface of `timetug-engine-c`. Decide for yourself whether a status bar exists and what it shows, how
the takeover looks, and where settings live.
