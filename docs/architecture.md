# Architecture

This is the current module map. The [2026-09-18 core design](superpowers/specs/2026-09-18-timetug-core-design.md) records original rationale; later ADRs and code supersede changed details.

## Modules
- The [timetug-shared](https://github.com/binary-companion/timetug-shared) repository (ADR 0020), consumed by released version, holds `TimeTugCore`, `CalendarBridge` and `TimeTugEngine` (below) with their tests and the dedup benchmark; Windows is a CI target there.
- `TimeTugCore` (`Sources/TimeTugCore` in `timetug-shared`): pure Swift; depends only on `CalendarCore`. `TimeTugCalendarEvent` model (wraps the library `CalendarEvent`, adds merge and display state), `CalendarSource` protocol, `CalendarStore`
  (merge/dedupe/last-good), duplicate rules, resolver, lessons and the adjudicator interface (ADR 0009), `TakeoverPolicy`, `TakeoverLedger` + `Scheduler`,
  `DayAgenda`, `TakeoverRequest`, `TakeoverSettings` (including `enabled`), `WidgetSnapshot` and `WidgetTimeline` (widget data and entry dates, ADR 0010). Note: `additionalCalendarKeys` tracks when a meeting
  appears on multiple opted-in calendars so takeover opt-in on any calendar counts.
- `TimeTugEngine` (`Sources/TimeTugEngine` in `timetug-shared`, [phase 3 spec](superpowers/specs/2026-10-15-phase-3-engine-design.md)): the portable "what and when" every front end shares. One `Engine` actor owns the sources and account lifecycle (`AccountManager`, reconcile, refresh coalescing), the `CalendarStore`, the takeover ledger and fire guard, launch acknowledgement, UI ticks, dedup actions and their persistence, the behaviour settings (through the host's `SettingsStorage`) and prompt building and answer parsing for a host `TextGenerator`. Front ends send `EngineCommand`s and observe `EngineState` (revisioned) and `EngineEvent`s (`takeoverDue`, `widgetSnapshot`, `joinRequested`, diagnostics). No display strings, no platform imports.
- `Packages/EventKitSource`: Apple Calendar adapter. Only place EventKit is imported.
- The [calendar-connectors](https://github.com/binary-companion/calendar-connectors) repository: the portable calendar connector library (ADR 0012), no external dependencies, consumed by released version. Products: `CalendarCore` (model, `AllDay`, `ConferenceDetector`, `JoinURLPolicy`, file-backed connection and sync-state stores, optional write API), `CalendarOAuth` (PKCE and refresh), `GoogleCalendar`, `MicrosoftCalendar`, `ICalendar`, `CalDAVCalendar` (including iCloud), `ICalSubscription` and `CalendarTestSupport`. The app supplies OAuth configuration and credentials (see [operations](development/runbooks/operations.md)). Microsoft sign-in requests read-only scopes under [ADR 0017](decisions/0017-microsoft-read-only-scopes.md); the library's write implementation remains available for a host that grants wider scopes.
- `CalendarBridge` (`Sources/CalendarBridge` in `timetug-shared`): minimal glue. `EventMapper` wraps library events (drops cancelled, adds calendar info); `ConnectedSource` adapts a library source to Core and translates errors and changes.
- `Packages/CalendarApple`: Keychain credential store, loopback OAuth and `CryptoKitSHA256` for the library.
- `Packages/AppleIntelligenceInference`: Apple's on-device model as the engine's `TextGenerator` (macOS 26+, compile-guarded); the prompt and answer parsing live in the engine. Only place with Foundation Models imports.
- `Apps/macOS`: menu bar item, popover, overlay windows, settings, and the engine host (`AppCoordinator`, with the adapters in `Sources/EngineAdapters`). `SettingsStore` keeps the presentation settings and mirrors the engine's behaviour settings; `AccountsController` mirrors the engine's account status. XcodeGen builds direct and App Store distributions from one specification; they share an App Group but use separate build directories. The App Store target excludes Sparkle.
- `Apps/macOS/Widgets`: WidgetKit extension (Next Up, Today, macOS 26 controls) that reads the app-written snapshot from the App Group; `Apps/macOS/Shared` holds the code compiled into both targets (ADR 0010).
  The optional global popup shortcut uses the KeyboardShortcuts package (ADR 0005), app layer only.

## Dependencies

`TimeTugCore -> CalendarCore`; `CalendarBridge -> TimeTugCore + CalendarCore` (both in `timetug-shared`, which depends on the connector library by range); `EventKitSource -> CalendarCore`; `CalendarApple -> CalendarCore + CalendarOAuth`. `TimeTugEngine -> TimeTugCore + CalendarBridge + CalendarCore`. The inference package depends on `timetug-shared` (TimeTugCore, TimeTugEngine); the app depends on `timetug-shared` (TimeTugCore, CalendarBridge, TimeTugEngine). Inside the library: `CalendarOAuth`, `ICalendar` and `CalendarTestSupport` depend on `CalendarCore`; Google and Microsoft each depend on `CalendarCore + CalendarOAuth`; CalDAV and iCal subscriptions each depend on `CalendarCore + ICalendar`. The app composes these packages. Keep this map aligned with the package manifests and `scripts/ci/check-architecture.sh`; the rules for Core and Bridge are enforced by the same script in `timetug-shared`.

## Flow
EventKit, Google, Microsoft, CalDAV and iCal subscriptions -> `CalendarBridge.ConnectedSource` -> (engine) `CalendarStore.refresh` (fetch window) -> `CalendarSnapshot` -> `Scheduler.next` -> one sleep on the engine clock
-> `EngineEvent.takeoverDue` -> (app) `OverlayController` -> join, snooze, dismiss or closed back to the engine. `EngineState.agenda` (`DayAgenda`) feeds the popover and the status title.
Engine -> `EngineEvent.widgetSnapshot` -> (app) group container (`agenda-snapshot.json`) -> widget timelines. Control Center intents write shared settings and post a Darwin notification; the app sends `settingsChangedExternally` and the engine re-reads them. The app reports wake, clock, time zone, day and network changes as `SystemEvent`s.

## Adding a calendar source
Implement the library's `CalendarSource` and `ConnectorKind` in the `calendar-connectors` repository: a library pull request, then the automatic "Bump calendar-connectors" pull request here (see AGENTS.md, Repositories, and the `working-across-timetug-repos` skill). Apple Calendar is the exception: it uses `EventKitSource`. Use `CalendarCore` models and errors; add `WritableCalendarSource` only for supported writes. Map the source through `CalendarBridge.ConnectedSource` and register its connector kind in `Apps/macOS/Sources/AppConnectors.swift`. The app supplies credentials, OAuth interaction and source configuration UI. Never import UI frameworks into the connector library or leak provider types into Core. A new package also needs its allowed dependencies and import rules in `scripts/ci/check-architecture.sh`, which fails until it has them.

## Adding a platform front end
Drive a `TimeTugEngine` `Engine` (or, below phase 4's C interface, depend on `TimeTugCore` only). Decide for yourself whether a status bar exists and what it shows, how
the takeover looks, and where settings live.
