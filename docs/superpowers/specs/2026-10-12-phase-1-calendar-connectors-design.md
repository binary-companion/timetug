# Phase 1: the `calendar-connectors` repository

Status: draft for the owner's review (2026-10-12). Parent: [program design](2026-10-09-windows-program-design.md), roadmap row 1 and section 1. The program design wins where the two disagree, except for the amendments in "Decisions" below, which also change the program design.

## Purpose

Move the connector library out of the Mac app's repository into its own public repository, `binary-companion/calendar-connectors`, so that the Windows engine (phase 2 onward) and any other front end can depend on it by released version. The Mac app keeps working throughout and consumes the library by a pinned release.

Success means: the repository exists with the library's history, `1.0.0` is tagged, every merge releases automatically, `timetug` builds and ships from the released tag, and a library change reaches `timetug` as a bump pull request without anyone editing two repositories by hand.

## Not in this phase

- No behaviour change in the library or the app. The flip pull request changes where the library comes from, not what it does.
- No `timetug-shared`, no engine, no Windows CI (phase 2 and later). The library is built on macOS and Linux only; Spike S already built it on Windows 11 ARM.
- No change to how the Mac app is released (draft, publish, approve).

## Decisions

| Topic | Decision |
|---|---|
| `CalendarApple` | **Stays in `timetug`** (amends program design section 1, which put it in the library repository). It only implements the library's seams (`CredentialStore`, `SHA256Hashing`, the OAuth redirect interaction), has one consumer, and the Windows adapters will live in `timetug-windows` in the same way. The library repository therefore has no platform conditions in its manifest. Moving it later is a plain extraction if an outside Apple consumer appears. Owner decision, 2026-10-12. |
| License | MIT (owner, 2026-10-12). `timetug` keeps its Commons Clause license; the library is licensed separately. |
| Tag format | Plain `X.Y.Z` (no `v`). `v*` tags are the owner-only release tags of the app repositories; the library's tags are created by its release workflow with the repository token. |
| Default branch | `main`, as the program design says for library repositories. |
| Version ranges | Libraries use ranges, apps pin exactly (program design, Pinning). Phase 1 applies this to `timetug`: local packages say `from: "1.0.0"`, `project.yml` says `exactVersion`. |
| Pin file | The program design says the Mac app pins in `project.yml` "with its `Package.resolved` committed". The app has none: the Xcode project is generated by XcodeGen and git-ignored, and no resolved file is tracked today. The pin is `exactVersion` in `project.yml` (as Sparkle's is), and a contract test keeps the local manifests' ranges compatible with it. Amends the program design's Pinning section. |
| History | Extracted with `git filter-repo` from a fresh clone (run with `uvx git-filter-repo`; it is not installed). Pull requests and issues are not carried over. |

## CI and releases in the library

- **`ci.yml`** on pull requests and pushes to `main`: a macOS job (`swift test` on the whole package, newest Xcode, as today) and a Linux job (the `swift:6.x` container used by `core-linux`, with the Docker Hub login from the organization secrets). A third job, `architecture`, runs `scripts/ci/check-architecture.sh` (the library's portability and layering rules, moved from `timetug`) and `scripts/ci/check-repository-contracts.py` (the copy the program design requires in every repository: no `pull_request_target`, no secret outside an approved environment). All three jobs are required checks on `main`. Action pins follow `docs/development/action-pins.md`.
- **`release.yml`** on push to `main` (and `workflow_dispatch` with a `version` input, used for `1.0.0` and for recovery). Every job declares its own `permissions:` (the organization default token is read-only): `publish` needs `contents: write` and `pull-requests: read` (to read the merged pull request's labels); `notify` needs none. **A push event never releases while the repository has no `X.Y.Z` tag**: the first push of the extracted history also starts this workflow, and without the guard it would invent a version before `1.0.0` is dispatched.
  1. Find the merged pull request for the commit and read its `semver:major`, `semver:minor` or `semver:patch` label (highest wins; none means patch).
  2. Compute the next `X.Y.Z` from the newest tag (the dispatch input overrides it; a push with no tag and no input stops here with a notice).
  3. In the `publish` environment (default branch only, no reviewer, admin bypass off): create the tag and a GitHub release with generated notes, using the repository token, so no key is stored.
  4. In the `bump` environment: mint a `timetug-bot` token and send `repository_dispatch` (`library-released`, with library name and version) to each dependent. Dependents today: `timetug`.
- **Rulesets** (applied with the same shape as `timetug`'s): `Protect main` (pull request, required checks, no deletion, no force push) and a tag ruleset on `refs/tags/*` that blocks update, deletion and non-fast-forward but not creation, so published versions are immutable and the release workflow can still create them.
- **Code index:** the `add-code-indexing` skill's workflow and pinned script, as program design section 1 requires.
- **Audit:** `scripts/security/audit-github.sh --strict` passes for the new repository (no repository-level secrets, protected default branch, environments without admin bypass). The release-tag rule of the audit applies only to repositories that ship signed `v*` releases, so the library is not added to that list.

## How `timetug` consumes it

- **Manifests:** `Packages/TimeTugCore`, `CalendarBridge`, `CalendarApple`, `EventKitSource` and `AppleIntelligenceInference` replace `.package(path: "../CalendarConnectors")` with `.package(url: "https://github.com/binary-companion/calendar-connectors", from: "1.0.0")`. Their product dependencies name the package `calendar-connectors`.
- **App:** `Apps/macOS/project.yml` replaces the `CalendarConnectors` path package with the URL and `exactVersion: 1.0.0`, as Sparkle is pinned. The Xcode project stays generated and git-ignored, so there is no `Package.resolved` to commit.
- **Contract test:** `scripts/ci/check-repository-contracts.py` fails when a shared-library dependency is a `path`, `branch` or `revision`, or when `project.yml` pins a shared library without `exactVersion`. This implements the program design's "an app never ships an unreleased shared commit".
- **Bump flow:** `.github/workflows/bump-dependencies.yml` runs on `repository_dispatch`, in the `bump` environment, mints a `timetug-bot` token (so the pull request's CI runs), updates `exactVersion` (and the range floor in the local manifests when the release raises it) and opens "Bump calendar-connectors to X.Y.Z" with the release notes. It never merges. Dependabot covers GitHub Actions and the manifests' URL dependencies as a safety net.
- **Local work on the library:** `scripts/dev/use-local-connectors.sh <path>` points the local packages and `project.yml` at a sibling checkout for the duration of a change and refuses to commit in that state (the contract test catches it). The cross-repository skill `working-across-timetug-repos` documents the loop: library pull request, merge, automatic release, bump pull request.
- **Repository guards that name the old path** are reworked in the flip pull request: `check-architecture.sh` and its test (the library rules leave; a rule that the five packages may depend on `calendar-connectors` by URL remains), `check-repository-contracts.py`, `verify.sh`, `affected-tests.sh` and their tests, `ci.yml` (`core` and `core-linux` stop testing the library), `AGENTS.md`, `docs/architecture.md`, `docs/development/runbooks/operations.md`, the `running-live-calendar-tests` skill and ADR links.

## Sequence

Each step leaves the Mac app releasable.

1. **(owner)** Publish `v2.1.0` so the new feed URL ships before anything moves (the phase 0 release; tracked separately).
2. **(owner)** Create the `timetug-bot` GitHub App (contents and pull-request write, metadata read; installed on the dependents only, today `timetug`: a token minted for a target repository needs the installation there, not on the repository whose workflow mints it) and add `actions/create-github-app-token`, pinned by SHA, to the organization's Actions allow-list. The agent then stores the app id and key in the `bump` environments.
3. Create the repository, extract the history, add the files above, rulesets, environments and the index, and run the first CI. Tag `1.0.0` through the dispatch input. From here until step 4 merges, the in-repo copy is frozen: library changes wait.
4. **Flip pull request in `timetug`:** delete `Packages/CalendarConnectors`, switch the five manifests and `project.yml` to the tag, rework the guards and docs listed above. Full CI, including the app tests, the App Store build and the DMG, must pass. The owner merges; the next beta carries it.
5. **Drill:** merge a docs-only change to the library with no label. A `1.0.1` release must appear and the bump pull request must open in `timetug` with passing CI without a manual step. Only then is the phase done.
6. Tracker, `AGENTS.md` Repositories section in both repositories, and the cross-repository skill.

## Verification

| Claim | Evidence |
|---|---|
| History preserved | `git log --follow` on a known file in the new repository reaches the 2026-09-20 first commit; commit count on the path matches (21). |
| Library builds without TimeTug | The repository's own CI on macOS and Linux, from a clone with no other checkout. |
| `1.0.0` equals the code `timetug` last shipped | The flip pull request's diff outside manifests, scripts and docs is empty; the app's tests pass unchanged. |
| Tags are immutable | A deliberate tag update is refused by the ruleset. |
| The bot cannot merge | Its pull request needs the owner's merge; the audit shows no bypass actor for it. |
| Automatic loop works | The step 5 drill. |

## Risks

| Risk | Mitigation |
|---|---|
| Library changes land in `timetug` between extraction and the flip and are lost | Freeze (step 3 to 4); the flip pull request diffs the extracted tree against `Packages/CalendarConnectors` at merge time and fails if they differ. |
| CI resolves a remote package and gets slower or flaky | Keep the existing SwiftPM cache step; measure the app job before and after; a failed resolve is retried once by SwiftPM and by the job. |
| The ruleset blocks the release workflow from creating tags | Test a throwaway tag in step 3 before relying on it; the dispatch input is the recovery path. |
| `repository_dispatch` needs a token with write access to the target | The bot token, minted from the `bump` environment; verified in the drill. |
| An app builds against a different library version than its sibling packages | Local manifests carry a range that includes the pinned version, and `project.yml`'s exact pin wins; the contract test checks that the pin satisfies every range. |
| The per-package jobs (`swift test --package-path Packages/TimeTugCore`) resolve the newest compatible library, which can be ahead of the app's `exactVersion` until the bump pull request merges | Accepted: the library's own semver promise covers it, and the `app` job, which builds the pinned version, is the authority for what ships. |
| Public API compatibility is now a real promise | `docs/api.md` is the contract; `semver:major` is required for a breaking change, and the label reminder sits in the library's pull request template. |
