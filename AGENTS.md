# TimeTug agent guide

Start with [current architecture](docs/architecture.md), then [development and verification](docs/development.md). The [original core design](docs/superpowers/specs/2026-09-18-timetug-core-design.md) is historical where later code or [ADRs](docs/decisions/README.md) differ. The shared agent rules cover semantic indexing and Serena; repository-specific task procedures live in [`.agents/skills`](.agents/skills/).

## Boundaries

- `TimeTugCore` answers what and when. It and `CalendarBridge` live in their own repository, [binary-companion/timetug-shared](https://github.com/binary-companion/timetug-shared), consumed by released version (`Apps/macOS/project.yml` pins it with `exactVersion`; `AppleIntelligenceInference` says `from:`); to change them, use the `working-across-timetug-repos` skill. Rules unchanged: pass `now: Date`; keep UI, Apple imports and display strings out of Core. Test each Core behavior with Swift Testing, writing the failing test first, in `timetug-shared`.
- The connector library is its own repository, [binary-companion/calendar-connectors](https://github.com/binary-companion/calendar-connectors), consumed by released version (`Apps/macOS/project.yml` pins it with `exactVersion`; the local packages say `from:`); to change it, use the `working-across-timetug-repos` skill. It is portable and dependency-free. Its `CalendarCore` model underpins Google, Microsoft, CalDAV, iCal subscriptions and Core. `CalendarOAuth` handles PKCE and refresh. `CalendarBridge` (in `timetug-shared`) connects library sources to Core; `EventKitSource` and `CalendarApple` contain Apple adapters. Only `AppleIntelligenceInference` imports Foundation Models.
- `Apps/macOS` composes sources, UI, widgets and Sparkle. `AppConnectors.swift` registers providers; the app owns credentials, source configuration and presentation. The direct and App Store targets share an App Group but must use separate build directories. Keep Sparkle imports inside `#if !APPSTORE`.
- Calendar writes are opt-in through `WritableCalendarSource`; unsupported fields throw `WriteError.unsupported`, and stale versions are resolved per touched field. Microsoft sign-in currently requests read-only scopes under [ADR 0017](docs/decisions/0017-microsoft-read-only-scopes.md); its library write implementation remains. Do not change scopes or capabilities incidentally.
- App state belongs in the App Group; credentials belong in Keychain. Use `AppSupportFiles.url(_:)` for app state and `WidgetSnapshotStore` for the widget snapshot; never construct a path under the real home directory for a sandboxed build. Keep secrets and certificates out of git. Record significant decisions in `docs/decisions/`.

## Repositories

- `calendar-connectors`: the connector library (MIT). Tags `X.Y.Z`, released automatically on every merge to `main`.
- `timetug-shared`: `TimeTugCore` and `CalendarBridge` (MIT plus the Commons Clause), with the Core and Bridge tests and the dedup benchmark (`scripts/benchmarks/run-dedup.sh`). Tags `X.Y.Z`, released automatically on every merge to `main`; its CI runs on macOS, Linux, Windows x64 and Windows ARM64 (see [ADR 0020](docs/decisions/0020-timetug-shared-repository.md)). It depends on `calendar-connectors` by range.
- `timetug-windows` (later) joins them per the [program design](docs/superpowers/specs/2026-10-09-windows-program-design.md).
- `timetug` (this repository): the Mac app, the Apple adapters and the product website.

A `calendar-connectors` release sends this repository a "Bump calendar-connectors to X.Y.Z" pull request: the library's `notify` job dispatches to `.github/workflows/bump-dependencies.yml`, which runs `scripts/ci/bump-pin.sh calendar-connectors X.Y.Z` and opens the pull request as `timetug-bot` so CI runs on it; the workflow never merges; the owner merges. The same workflow takes a `timetug-shared` release (`library` is `calendar-connectors` or `timetug-shared`, in the dispatch payload or the manual input): it also raises the connector pin to the version that release's `Package.resolved` records, never lowering it. The chain from a `timetug-shared` release to that dispatch (its `notify` job, and its own bump workflow for connector releases) is planned and not live yet. Each pin is never edited by hand except through `bump-pin.sh <calendar-connectors|timetug-shared> X.Y.Z`: it always moves `exactVersion` and raises the `from:` floors in the `Packages/*/Package.swift` manifests only on a major bump (`--at-least` leaves a pin that is already at or above the version alone). Raise a floor by hand only when the code needs a new version; `scripts/ci/check-shared-pins.py` verifies that every floor is at most the pin and within one major, for both libraries. For work across repositories, `scripts/dev/use-local-library.sh <calendar-connectors|timetug-shared> <path>` points the app at a library checkout (`use-local-connectors.sh` stays as a wrapper for the connector library); never commit its output. The `working-across-timetug-repos` skill has the steps and the recovery when a bump does not arrive.

## Verify

Run `scripts/dev/verify.sh affected` for local changes, or choose `core`, `connectors`, `app`, `release-tools`, or `all`. `affected --base <ref>` includes changes since a base. `scripts/dev/affected-tests.sh` prints the narrower dependency-ordered commands when useful. Logs and a per-run summary go to `build/verify/`. `all` runs package, app and release-tool checks. Core and Bridge tests and Linux and Windows portability run in `timetug-shared`'s CI; [manual macOS UI checks](docs/manual-tests/macos-checklist.md) and live provider writes remain separate evidence. The wrapper never enables live tests. See [development](docs/development.md) for prerequisites and checkpoints.

`xcodegen generate --spec Apps/macOS/project.yml` regenerates the ignored Xcode project. `project.yml` owns generated Info.plist properties for both distributions and widgets. Do not discard privacy descriptions, entitlements, OAuth substitutions or Sparkle keys. Use the [operations runbook](docs/development/runbooks/operations.md) and the task skills under `.agents/skills/` for signing, OAuth, widgets, CI and live-test procedures.

## Release boundary

PR CI and website validation do not deploy or sign releases. Merged `site/` changes deploy through Firebase Hosting; beta and release workflows use protected environments after merge. A green local check is not a merge, deployed site or published release. Follow [release rules](docs/release.md) and the [site guide](site/README.md) for deployment and production checks.
