# TimeTug agent guide

Start with [current architecture](docs/architecture.md), then [development and verification](docs/development.md). The [original core design](docs/superpowers/specs/2026-09-18-timetug-core-design.md) is historical where later code or [ADRs](docs/decisions/README.md) differ. The shared agent rules cover semantic indexing and Serena; repository-specific task procedures live in [`.agents/skills`](.agents/skills/).

## Boundaries

- The Mac app runs on the Rust engine (ADR 0023). `timetug-shared` 2.x carries the engine (core, connectors, accounts, refreshes, the takeover ledger and fire guard, dedup actions, the behaviour settings) behind one `Engine` that front ends drive with commands and observe through state and events; the app and its local packages import only `TimeTugKit` (`Apps/macOS/project.yml` pins `timetug-shared` with `exactVersion`; the local packages say `from:`). The XCFramework is prebuilt, so building the app needs no Rust toolchain. To change the engine, use the `working-across-timetug-repos` skill: the change is Rust in `timetug-shared` (or `calendar-connectors`), released, and then bumped here. No Rust is written in this repository. Rules unchanged: pass `now: Date` where the app still computes dates; keep UI, Apple imports and display strings out of the engine. Test engine behaviour in `timetug-shared`, writing the failing test first.
- The connector library is its own repository, [binary-companion/calendar-connectors](https://github.com/binary-companion/calendar-connectors) (Rust from 2.0.0). The app does not depend on it: the connectors come inside `TimeTugKit`. To change a connector, use the `working-across-timetug-repos` skill. `EventKitSource` and `CalendarApple` contain the Apple adapters that implement the generated host interfaces. Only `AppleIntelligenceInference` imports Foundation Models.
- `Apps/macOS` is a thin host over the engine: `AppCoordinator` builds one `Engine` (`AppConnectors.makeConfig`) from the Mac adapters (`Sources/EngineAdapters`: settings storage over today's UserDefaults keys, OSLog diagnostics, the state mirror and ordered command lanes; EventKit, Keychain, the credential sheet and Apple Intelligence), sends commands and renders state. It owns presentation: UI, the presentation settings (menu bar mode, appearance, popup card style), widgets and Sparkle. For every `takeoverDue` it sends exactly one closing command (join, snooze, dismiss or `takeoverClosed`). `AppConnectors.swift` registers providers; the app owns credentials, source configuration and presentation. The direct and App Store targets share an App Group but must use separate build directories. Keep Sparkle imports inside `#if !APPSTORE`.
- Calendar writes are opt-in through `WritableCalendarSource`; unsupported fields throw `WriteError.unsupported`, and stale versions are resolved per touched field. Microsoft sign-in currently requests read-only scopes under [ADR 0017](docs/decisions/0017-microsoft-read-only-scopes.md); its library write implementation remains. Do not change scopes or capabilities incidentally.
- App state belongs in the App Group; credentials belong in Keychain. Use `AppSupportFiles.url(_:)` for app state and `WidgetSnapshotStore` for the widget snapshot; never construct a path under the real home directory for a sandboxed build. Keep secrets and certificates out of git. Record significant decisions in `docs/decisions/`.

## Repositories

- `calendar-connectors`: the connector library (MIT), Rust. Tags `X.Y.Z`, released automatically on every merge to `main` (2.x since 2026-11-14) and, for the old Swift line, to `1.x` (1.x releases; the Mac no longer uses them).
- `timetug-shared`: the Rust engine and its tests (including the conformance suite and the dedup benchmark `scripts/benchmarks/run-dedup.sh`), the C interface for Windows and the generated Swift package `TimeTugKit` with its prebuilt `TimeTugEngineFFI.xcframework` (MIT plus the Commons Clause). Tags `X.Y.Z`, released automatically on every merge to `main`; its CI runs on macOS, Linux, Windows x64 and Windows ARM64 (see [ADR 0020](docs/decisions/0020-timetug-shared-repository.md)). It depends on `calendar-connectors` by range.
- `timetug-windows`: the Windows app (C# and WinUI), on `TimeTug.Engine` 2.x (the Rust engine) from nuget.org.

Both libraries are Rust from 2.0.0 (the Rust engine program, [ADR 0022](docs/decisions/0022-shared-libraries-in-rust.md)). **The Mac is on `TimeTugKit` 2.x ([ADR 0023](docs/decisions/0023-mac-app-on-rust-engine.md)) and no `1.x` pin is left in this repository.** The `1.x` branches of both libraries (the Swift line) stop serving the Mac once the cutover release ships; they are kept for history and for users of old Mac builds only, and a Swift fix for the Mac is no longer made.
- `timetug` (this repository): the Mac app, the Apple adapters and the product website.

Since phase 6 of the Rust program the Mac app pins one library, `timetug-shared` 2.x (product `TimeTugKit`; the connectors come inside it). A `timetug-shared` release dispatches `library-released` from its `notify` job to this repository: `.github/workflows/bump-dependencies.yml` runs `scripts/ci/bump-pin.sh timetug-shared X.Y.Z` and opens "Bump timetug-shared to X.Y.Z" as `timetug-bot` so CI runs on it, and closes the open bump pull requests it makes redundant ("Superseded by #N"). A `calendar-connectors` dispatch ends with a notice (nothing to bump), and `bump-major-guard.sh` holds a major above the pinned one (3.0.0). The workflow never merges; the owner merges. A missed dispatch is recovered by hand: `gh workflow run "Bump dependencies" --repo binary-companion/timetug -f library=timetug-shared -f version=X.Y.Z`. The pin is never edited by hand except through `bump-pin.sh timetug-shared X.Y.Z` (`calendar-connectors` is refused): it always moves `exactVersion` and raises the `from:` floors in the `Packages/*/Package.swift` manifests only on a major bump (`--at-least` leaves a pin that is already at or above the version alone). Raise a floor by hand only when the code needs a new version; `scripts/ci/check-shared-pins.py` verifies that every floor is at most the pin and within one major, and that no `calendar-connectors` entry is left. For work across repositories, `scripts/dev/use-local-library.sh timetug-shared <path>` points the app at a checkout of `timetug-shared` (its `build/TimeTugEngineFFI.xcframework` is built first by that checkout's `scripts/dev/build-xcframework.sh` when missing); never commit its output. The `working-across-timetug-repos` skill has the steps and the recovery when a bump does not arrive.

## Tracking work

Features and fixes are tracked in GitHub issues and the org projects TimeTug and Libraries, not in progress documents. Use the [`tracking-work-in-issues`](.agents/skills/tracking-work-in-issues/SKILL.md) skill to create, plan, execute and close issues and sub-issues, to set status and the Agent field, and to file owner steps as Manual Tasks in the private `binary-companion/manual-configuration` repository. Each issue must be readable on its own; link plan documents for large work. Specs and plans stay in `docs/superpowers/`. Every pull request is attached to an issue: `Fixes #N` when it finishes it, `Part of #N` when it only advances it; the tracking check fails a PR that mentions none.

## Verify

Run `scripts/dev/verify.sh affected` for local changes, or choose `core`, `connectors`, `app`, `release-tools`, or `all`. `affected --base <ref>` includes changes since a base. `scripts/dev/affected-tests.sh` prints the narrower dependency-ordered commands when useful. Logs and a per-run summary go to `build/verify/`. `all` runs package, app and release-tool checks. Core and Bridge tests and Linux and Windows portability run in `timetug-shared`'s CI; [manual macOS UI checks](docs/manual-tests/macos-checklist.md) and live provider writes remain separate evidence. The wrapper never enables live tests. See [development](docs/development.md) for prerequisites and checkpoints.

`xcodegen generate --spec Apps/macOS/project.yml` regenerates the ignored Xcode project. `project.yml` owns generated Info.plist properties for both distributions and widgets. Do not discard privacy descriptions, entitlements, OAuth substitutions or Sparkle keys. Use the [operations runbook](docs/development/runbooks/operations.md) and the task skills under `.agents/skills/` for signing, OAuth, widgets, CI and live-test procedures.

## Release boundary

PR CI and website validation do not deploy or sign releases. Merged `site/` changes deploy through Firebase Hosting; beta and release workflows use protected environments after merge. A green local check is not a merge, deployed site or published release. Follow [release rules](docs/release.md) and the [site guide](site/README.md) for deployment and production checks.
